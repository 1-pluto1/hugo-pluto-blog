### Abstract

专为代码智能设计的大型语言模型和深度学习模型，因其能够执行各种与代码相关的任务，已经给软件工程领域带来了革命性的变革。在代码补全、缺陷检测和代码摘要等任务中，这些模型能够高精度地处理源代码和软件工件；因此，它们有潜力成为现代软件工程实践中不可或缺的一部分。

尽管具备这些能力，但**鲁棒性**（robustness）对于深度代码模型而言，仍然是一项关键的质量属性，因为它们在多变和对抗性的条件下（例如，对变量进行重命名）可能会产生不同的结果。**蜕变测试**（Metamorphic testing）已成为一种广泛用于评估模型鲁棒性的方法，其具体做法是：对输入程序应用**“保义转换”**（semantic-preserving transformations），并分析模型输出的稳定性。

尽管已有研究探索了深度学习模型的测试方法，但这篇系统性文献综述专门聚焦于针对深度代码模型的蜕变测试。通过对45篇主要研究论文的学习，我们分析了其中用于评估鲁棒性的（代码）转换、技术和评估方法。我们的综述总结了当前的研究现状，明确了常被评估的模型、编程任务、数据集、目标语言和评估指标，并强调了推动该领域发展的关键挑战与未来方向。

### INTRODUCTION

近年来，面向代码的大语言模型（LLM4Code）在一系列软件工程任务中取得了卓越的性能，其准确率水平使其在现实世界中的应用变得越来越可行。这些任务包括但不限于程序修复 [1]、漏洞检测 [2, 3]、代码补全 [4, 5] 和克隆检测 [6, 7] 等。

然而，LLM4Code 的实际适用性不仅取决于它们在下游任务中的性能，还取决于它们在多大程度上满足非功能性需求，例如鲁棒性（robustness）[8, 9, 10]、可持续性 [11, 12]、安全性 [13] 和数据隐私 [14, 10]。例如，Yang 等人 [15] 的研究表明，LLM4Code 常常无法满足许多非功能性需求，其中对对抗性代码的鲁棒性尤为关键。Hammond 等人 [13] 发现，由 GitHub Copilot 生成的代码中，约有 40% 受到了安全漏洞的影响。在这些需求中，鲁棒性之所以特别重要，是因为大语言模型可能仅仅因为开发者使用了不同的变量名或编码规范，就无法识别出安全漏洞或修复错误 [12]。

传统的测试方法，如模糊测试（fuzzing）[16] 和测试数据生成 [17]，虽然可以为大语言模型生成新的代码片段（输入数据），但需要模型分析师手动验证输出的正确性。具体而言，为给定输入确定预期输出不仅耗时，而且容易出现人为错误，尤其是在面对生成的代码时。这个问题通常被称为“谕言机问题”（oracle problem）[18]。

蜕变测试（Metamorphic Testing, MT）[19] 提供了一种有前景的替代方案，它通过使用“蜕变关系”来缓解谕言机问题。蜕变关系描述了当系统（在我们的案例中是 LLM）的输入被系统性地转换后，其输出应该如何表现。该技术基于这样一个前提：推理模型不同输出之间的关系，通常比完全理解模型自身的行为要简单得多 [19]。

对深度代码模型进行蜕变测试，是通过对模型输入（例如，一个代码片段）应用保持其执行行为不变的蜕变转换来执行的。然后，评估被测模型是否对原始输入和转换后的输入都产生相同的预测。例如，一个蜕变转换可以包括将 `for` 循环替换为等效的 `while` 循环，这保证了代码的功能性保持不变。通过将此类转换应用于大量代码片段，我们可以通过衡量模型的预测因输入被转换而发生变化的频率，来评估模型的鲁棒性。

在文献中，蜕变测试已被应用于测试许多应用领域的程序，例如 Web 服务 [20]、图像处理应用 [21] 和编译器测试 [22]。众多综述和研究综合分析了其在广泛领域中的应用 [19, 23, 24, 25]，进一步凸显了蜕变测试的持久价值。与本研究最相关的是 Segura 等人 [19] 在 2016 年发表的一篇综述，该文讨论了蜕变测试在包括经典机器学习（例如 WEKA 库）在内的 12 个领域中的使用情况。然而，这篇综述发表于大语言模型出现之前，并未考虑到深度代码模型带来的独特性质和挑战。近期，Rehman 等人 [26] 概述了蜕变测试在机器学习各领域的应用，例如蛋白质功能预测 [27] 和六种声学场景分类器 [28]。但他们的重点是更广泛的监督和非监督机器学习所面临的开放性挑战，而非针对代码相关任务的大语言模型。

由于近期研究工作的激增以及大语言模型（尤其是在代码相关任务中）报告的性能不断提升，研究人员已经提出了各种针对 LLM4Code 定制的蜕变测试技术。尽管研究日益增多，但文献中缺乏一个统一的概述，关于 LLM4Code 蜕变测试的出版物非常零散。这也是因为作者们在描述蜕变测试时使用了不同的术语，例如反事实样本、对抗性攻击或混淆技术。在撰写本文时，尚无全面的综述或系统性文献回顾来综合和分析这些研究，这使得评估当前技术水平和确定新的研究方向变得困难。

本文通过对 LLM4Code 的蜕变测试进行系统性回顾，填补了这一空白，对现有工作进行了深入分析，并指出了未来的研究机会。在这项研究中，我们呈现了一篇文献综述，审视了蜕变测试技术如何被应用于评估深度代码模型的鲁棒性。我们的研究发现总结在表1中。我们相信这些结果将在指导这个快速发展领域的未来研究和开发中发挥重要作用。

本研究提供以下主要贡献：

- 我们通过系统性文献综述（SLR）的方式研究了 45 篇关于深度代码模型蜕变转换的论文。所有论文都根据第3节中的方法进行了仔细的审查、分析和分类。我们对文献中使用的不同类型的蜕变转换进行了分类，并提供了一个分类体系。该体系根据这些转换的特性、目标以及对各种代码相关任务的适用性进行组织。
- 我们对深度代码模型中蜕变测试的各种应用技术进行了分类，并强调不仅转换的类型很重要，其应用方法——例如单次传递、基于采样、梯度引导或演化方法——对鲁棒性评估也至关重要。
- 我们识别并总结了通过蜕变测试最常被评估的深度代码模型、编程任务、数据集、评估指标和目标编程语言。这一分析为了解蜕变测试在代码相关任务中的应用趋势提供了见解。
- 我们概述了深度代码模型在进行蜕变测试时面临的局限性，并为研究人员提出了未来的方向，同时密切关注该领域的现有空白。

第2节总结了相关工作，并更详细地介绍了深度代码模型、蜕变转换及其应用的核心原则。第3节描述了我们的研究问题、用于筛选相关研究论文的方法、本研究的纳入和排除标准，以及从每项主要研究中收集的数据。我们的发现在第4节中进行了描述和总结，而第5节讨论了我们发现的开放挑战和未来研究方向。最后，我们的结论在第7节中呈现。

### BACKGROUND & RELATED WORKS

#### 2.1 Deep Code Models

近年来，软件工程界的研究人员已使用深度代码模型来（半）自动化各种与代码相关的任务，例如程序修复 [1]、漏洞检测 [2, 3] 和代码补全 [4, 5]。深度代码模型可分为三大类：(1) 面向代码的自然语言模型，(2) 预训练代码模型，以及 (3) 通用大语言模型 (LLM)。

**面向代码的自然语言模型** 专注于学习代码片段的紧凑表示，并直接在代码数据上进行训练。这些模型通过整合诸如抽象语法树 (AST) 和控制流图等结构化信息，从代码片段中提取嵌入。此类模型中的代表是 code2vec [29] 和 code2seq [30]。code2vec [29] 使用神经网络将代码片段表示为固定长度的向量，而像 GGNN（门控图神经网络）[31] 这样基于图的模型则将代码建模为图。这类模型是直接为特定的软件工程任务进行训练和调整的。

**预训练代码模型** 是指在包括 GitHub 和 Stack Overflow 在内的大型软件数据集语料库上，使用自监督学习进行预训练的大语言模型 (LLM)。例如，CodeBERT [32] 是一个在代码和自然语言描述上训练的双峰 Transformer 模型，而 CodeT5 [33] 则将 T5 架构扩展到了代码领域。这些模型使用掩码语言建模或因果语言建模进行预训练。**掩码语言建模 (MLM)** 的做法是在输入序列中遮盖（mask）部分词元（token），并优化模型使其能根据周围（未被遮盖的）词元来预测被遮盖的词元。而**因果语言建模 (CLM)** 则是一种自回归方法，它优化模型使其能在给定前文词元的条件下，预测序列中的下一个词元。在预训练之后，这些模型会在特定任务的数据集上进行微调，以适应专门的下游任务。例如，DeepTyper [34] 就是为类型推断任务进行微调的。

**通用大语言模型 (LLM)** 的训练语料库超越了源代码，涵盖了多种类型，包括科学论文、书籍和更广泛的自然语言文档。这些模型通常包含数十亿个参数，能够执行广泛的自然语言处理任务，而无需针对特定应用进行微调。因此，这些模型能够执行代码之外的下游任务，但也可以通过提示工程进一步专门用于特定任务。

#### 2.2 Metamorphic Testing

蜕变测试（Metamorphic Testing）最初由 Chen 等人 [38] 提出，作为对“谕言机问题”（oracle problem）的一种解决方案，该问题指的是在某些情况下，确定给定输入的输出是否正确是不可行的 [18]。蜕变测试并不直接验证正确性，而是推理输入与输出之间的关系 [19]。例如，为了验证一个计算正弦函数（sine function）的系统，我们可以测试这样一种关系：若 L1 与 L2 满足某个关系 M，则 sin(L1) = sin(L2)。如果系统违反了这种预期的关系，即便没有测试谕言机，这种方法也能识别出错误。

将蜕变测试应用于深度代码模型，涉及到对代码片段进行“保义转换”（semantic-preserving transformations）。这些转换，例如将 `for` 循环替换为等效的 `while` 循环，会保持原始程序的执行行为。然后，通过衡量模型对原始样本和转换后样本的预测是否保持一致来评估其鲁棒性 [9]。

虽然蜕变测试已广泛应用于 Web 服务、模拟与建模、计算机图形学、嵌入式系统和机器学习等其他领域 [19]，但由于代码存在严格的句法和语法约束，它给代码模型带来了独特的挑战。例如，转换必须同时保持代码的语法和语义，这使得这些转换的自动生成和应用变得复杂。此外，转换可能会以特定于任务的方式改变输入-输出行为。Bielik 和 Vechev [39] 展示了用于类型推断任务的转换，例如改变整数字面量，其中改变后的输出对于该任务仍然是有效的。这凸显了蜕变测试对不同上下文的适应性。

目前，蜕变测试主要用于评估鲁棒性，正如本综述所分析的大多数主要研究中所反映的那样。它对保义转换的关注，为深度代码模型的鲁棒性评估提供了一种结构化的方法，解决了软件工程和代码人工智能领域的关键挑战。

图1阐释了应用于深度代码模型的蜕变测试的核心原理。从一个源代码输入开始，“转换选择器/测试用例生成器”首先确定要应用哪些转换。该组件可能使用单次传递、基于采样或梯度信息引导的选择策略。在此指导下，一系列保义转换（例如，变量重命名、无用代码插入或语句重排序）被应用于源代码，以产生逻辑上等价的代码变体。这些变体连同原始代码一起，被传递给被测系统（SUT），这通常是一个深度代码模型，如 CodeBERT 或 CodeT5。然后对输出进行比较：如果模型对语义上等价的输入产生了不一致的预测，则认为测试失败。这种方法无需谕言机标签即可进行鲁ebus评估，而是依赖于转换后输入的语义等价性作为一种隐式的谕言机。

#### 2.3 Scope of !ality A"ributes in Metamorphic Testing

尽管蜕变测试（MT）已被广泛用于评估**鲁棒性** [40, 41]，但其概念框架并不仅限于这一个质量属性。原则上，蜕变测试可以扩展用于评估更广泛的非功能性属性，包括**公平性** [42, 43, 44, 45, 46]、**可解释性**和**幻觉**。

然而，在当前的实践中，尤其是在深度代码模型评估领域，蜕变测试的应用仍主要集中在模型的鲁棒性上。这一趋势也反映在我们的综述中：所分析的全部45篇主要研究都使用蜕变测试来检验模型对输入扰动或保义转换的**韧性**，而非评估公平性或其他属性。

蜕变测试在支持鲁棒性之外的质量评估方面的更广泛潜力仍未得到充分探索，我们鼓励未来的工作研究如何扩展或调整蜕变测试技术，以解决基于大语言模型（LLM）系统中的公平性、幻觉检测和可解释性问题。

#### 2.4 Related Work

研究人员已经从深度代码模型维持其在输入微小扰动下保持性能恒定且正确的能力方面，对其**鲁棒性**进行了研究 [47]。鲁棒性失效可能导致严重问题，例如，对于具有不同编码风格或英语熟练度的用户生成不一致的输出，从而损害其可靠性 [48]。在一些高风险场景中，例如在负责检测受损漏洞的 CI/CD 流水线中，非鲁棒的模型可能会漏掉被修改过的漏洞，导致潜在的危险代码未经检测就通过。

鲁棒性测试通常分为**白盒**和**黑盒**方法 [47, 49]；白盒方法需要完全访问模型的结构、参数和训练数据，而黑盒方法则在无法访问这些信息的情况下工作 [49]。

尽管在评估深度代码模型的鲁棒性和应用蜕变测试方面已有大量的研究工作，但仍然存在显著的空白。Li 等人 [50] 对深度代码模型的鲁棒性进行了一项综述，重点关注用于提升鲁棒性的对抗性训练和修复技术。虽然他们的综述对对抗性方法提供了广泛的概述，但并未审视不同研究中用于测试鲁棒性的转换和方法。同样，Qu 等人 [51] 通过保义转换或对抗性攻击研究了鲁棒性评估，但他们的综述尽管在该主题上投入了大量精力，却未能提供对转换的完整分析或分类。例如，标识符重命名，作为一种流行的转换，在不同研究中的定义和阐述程度不一致，如表5所示。此外，Qu 等人遗漏了本研究中包含的许多相关研究，留下了巨大的覆盖空白。Rabin 等人 [52] 广泛探讨了深度代码模型的属性和质量，包括鲁棒性。然而，其主要焦点是通过实验评估和实现来理解这些模型，而不是进行综述或系统性文献回顾。Yang 等人 [47] 和 Hou 等人 [53] 提供了更广泛的系统性文献综述，关注代码大语言模型的多个方面和不同维度。他们的研究探讨了鲁棒性、安全性、隐私和可解释性。然而，他们的范围超出了鲁棒性，并且不仅仅关注测试方法。

早期的综述如 [23] 通过讨论蜕变测试的主要思想、一般性挑战和未来可能性，对其进行了广泛的概述。然而，我们的研究解决了一个更具体且更及时的课题：**将蜕变测试用于深度代码模型**。与以往的综述不同，我们系统性地审视了**哪些转换被使用、它们是如何被应用的，以及涉及了哪些模型、任务、数据集、语言和评估指标**。这种技术和实证层面的细节是前所未有的。此外，我们对挑战和未来方向的讨论直接基于我们在文献中观察到的模式和空白，而非基于一般性的假设。这使得我们的综述成为关于蜕变测试当前如何应用于深度代码模型评估的**第一篇详细且数据驱动的概述**。

与这些先前的工作相比，我们的研究将焦点专门缩小到蜕变测试，并对其在深度代码模型鲁棒性评估中的应用提供了深入的分析。我们系统地对转换类型进行分类，澄清了不一致的术语（例如，“蜕变测试”与“反事实样本”），并纳入了更广泛、更前沿的研究。这使我们能够填补文献中的关键空白，并提供关于 LLM4Code 蜕变测试实践的**第一篇全面综述**。

### METHODOLOGY


在开展系统文献综述的过程中，我们遵循了由Webster等[54]和Kitchenham等[55]建立的严谨方法论框架。Webster与Kitchenham的研究方法具有互补性：Webster倡导跨学科研究的融合，而Kitchenham则专门针对软件工程领域提出了系统综述的具体技术规范。本研究采用全面无偏的文献分析方法，对深度代码模型的蜕变测试研究进行系统性梳理。

#### 3.1 Research questions

为全面把握该领域的研究现状，我们提出了以下研究问题：
• RQ1：哪些类型的蜕变转换被用于评估深度代码模型的鲁棒性？
• RQ2：在鲁棒性评估中应用转换的技术有哪些？
• RQ3：哪些编程相关任务已通过蜕变测试进行评估？
• RQ4：哪些深度代码模型已通过蜕变测试进行验证？
• RQ5：用于深度代码模型蜕变测试的输入代码涉及哪些编程语言？
• RQ6：哪些数据集被用于生成蜕变转换和评估模型性能？
