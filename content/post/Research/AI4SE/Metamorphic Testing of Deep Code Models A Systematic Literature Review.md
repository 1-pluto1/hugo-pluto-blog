### Abstract

专为代码智能设计的大型语言模型和深度学习模型，因其能够执行各种与代码相关的任务，已经给软件工程领域带来了革命性的变革。在代码补全、缺陷检测和代码摘要等任务中，这些模型能够高精度地处理源代码和软件工件；因此，它们有潜力成为现代软件工程实践中不可或缺的一部分。

尽管具备这些能力，但**鲁棒性**（robustness）对于深度代码模型而言，仍然是一项关键的质量属性，因为它们在多变和对抗性的条件下（例如，对变量进行重命名）可能会产生不同的结果。**蜕变测试**（Metamorphic testing）已成为一种广泛用于评估模型鲁棒性的方法，其具体做法是：对输入程序应用**“保义转换”**（semantic-preserving transformations），并分析模型输出的稳定性。

尽管已有研究探索了深度学习模型的测试方法，但这篇系统性文献综述专门聚焦于针对深度代码模型的蜕变测试。通过对45篇主要研究论文的学习，我们分析了其中用于评估鲁棒性的（代码）转换、技术和评估方法。我们的综述总结了当前的研究现状，明确了常被评估的模型、编程任务、数据集、目标语言和评估指标，并强调了推动该领域发展的关键挑战与未来方向。

### INTRODUCTION

近年来，面向代码的大语言模型（LLM4Code）在一系列软件工程任务中取得了卓越的性能，其准确率水平使其在现实世界中的应用变得越来越可行。这些任务包括但不限于程序修复 [1]、漏洞检测 [2, 3]、代码补全 [4, 5] 和克隆检测 [6, 7] 等。

然而，LLM4Code 的实际适用性不仅取决于它们在下游任务中的性能，还取决于它们在多大程度上满足非功能性需求，例如鲁棒性（robustness）[8, 9, 10]、可持续性 [11, 12]、安全性 [13] 和数据隐私 [14, 10]。例如，Yang 等人 [15] 的研究表明，LLM4Code 常常无法满足许多非功能性需求，其中对对抗性代码的鲁棒性尤为关键。Hammond 等人 [13] 发现，由 GitHub Copilot 生成的代码中，约有 40% 受到了安全漏洞的影响。在这些需求中，鲁棒性之所以特别重要，是因为大语言模型可能仅仅因为开发者使用了不同的变量名或编码规范，就无法识别出安全漏洞或修复错误 [12]。

传统的测试方法，如模糊测试（fuzzing）[16] 和测试数据生成 [17]，虽然可以为大语言模型生成新的代码片段（输入数据），但需要模型分析师手动验证输出的正确性。具体而言，为给定输入确定预期输出不仅耗时，而且容易出现人为错误，尤其是在面对生成的代码时。这个问题通常被称为“谕言机问题”（oracle problem）[18]。

蜕变测试（Metamorphic Testing, MT）[19] 提供了一种有前景的替代方案，它通过使用“蜕变关系”来缓解谕言机问题。蜕变关系描述了当系统（在我们的案例中是 LLM）的输入被系统性地转换后，其输出应该如何表现。该技术基于这样一个前提：推理模型不同输出之间的关系，通常比完全理解模型自身的行为要简单得多 [19]。

对深度代码模型进行蜕变测试，是通过对模型输入（例如，一个代码片段）应用保持其执行行为不变的蜕变转换来执行的。然后，评估被测模型是否对原始输入和转换后的输入都产生相同的预测。例如，一个蜕变转换可以包括将 `for` 循环替换为等效的 `while` 循环，这保证了代码的功能性保持不变。通过将此类转换应用于大量代码片段，我们可以通过衡量模型的预测因输入被转换而发生变化的频率，来评估模型的鲁棒性。

在文献中，蜕变测试已被应用于测试许多应用领域的程序，例如 Web 服务 [20]、图像处理应用 [21] 和编译器测试 [22]。众多综述和研究综合分析了其在广泛领域中的应用 [19, 23, 24, 25]，进一步凸显了蜕变测试的持久价值。与本研究最相关的是 Segura 等人 [19] 在 2016 年发表的一篇综述，该文讨论了蜕变测试在包括经典机器学习（例如 WEKA 库）在内的 12 个领域中的使用情况。然而，这篇综述发表于大语言模型出现之前，并未考虑到深度代码模型带来的独特性质和挑战。近期，Rehman 等人 [26] 概述了蜕变测试在机器学习各领域的应用，例如蛋白质功能预测 [27] 和六种声学场景分类器 [28]。但他们的重点是更广泛的监督和非监督机器学习所面临的开放性挑战，而非针对代码相关任务的大语言模型。

由于近期研究工作的激增以及大语言模型（尤其是在代码相关任务中）报告的性能不断提升，研究人员已经提出了各种针对 LLM4Code 定制的蜕变测试技术。尽管研究日益增多，但文献中缺乏一个统一的概述，关于 LLM4Code 蜕变测试的出版物非常零散。这也是因为作者们在描述蜕变测试时使用了不同的术语，例如反事实样本、对抗性攻击或混淆技术。在撰写本文时，尚无全面的综述或系统性文献回顾来综合和分析这些研究，这使得评估当前技术水平和确定新的研究方向变得困难。

本文通过对 LLM4Code 的蜕变测试进行系统性回顾，填补了这一空白，对现有工作进行了深入分析，并指出了未来的研究机会。在这项研究中，我们呈现了一篇文献综述，审视了蜕变测试技术如何被应用于评估深度代码模型的鲁棒性。我们的研究发现总结在表1中。我们相信这些结果将在指导这个快速发展领域的未来研究和开发中发挥重要作用。

本研究提供以下主要贡献：

- 我们通过系统性文献综述（SLR）的方式研究了 45 篇关于深度代码模型蜕变转换的论文。所有论文都根据第3节中的方法进行了仔细的审查、分析和分类。我们对文献中使用的不同类型的蜕变转换进行了分类，并提供了一个分类体系。该体系根据这些转换的特性、目标以及对各种代码相关任务的适用性进行组织。
- 我们对深度代码模型中蜕变测试的各种应用技术进行了分类，并强调不仅转换的类型很重要，其应用方法——例如单次传递、基于采样、梯度引导或演化方法——对鲁棒性评估也至关重要。
- 我们识别并总结了通过蜕变测试最常被评估的深度代码模型、编程任务、数据集、评估指标和目标编程语言。这一分析为了解蜕变测试在代码相关任务中的应用趋势提供了见解。
- 我们概述了深度代码模型在进行蜕变测试时面临的局限性，并为研究人员提出了未来的方向，同时密切关注该领域的现有空白。

第2节总结了相关工作，并更详细地介绍了深度代码模型、蜕变转换及其应用的核心原则。第3节描述了我们的研究问题、用于筛选相关研究论文的方法、本研究的纳入和排除标准，以及从每项主要研究中收集的数据。我们的发现在第4节中进行了描述和总结，而第5节讨论了我们发现的开放挑战和未来研究方向。最后，我们的结论在第7节中呈现。

### BACKGROUND & RELATED WORKS

#### 2.1 Deep Code Models

近年来，软件工程界的研究人员已使用深度代码模型来（半）自动化各种与代码相关的任务，例如程序修复 [1]、漏洞检测 [2, 3] 和代码补全 [4, 5]。深度代码模型可分为三大类：(1) 面向代码的自然语言模型，(2) 预训练代码模型，以及 (3) 通用大语言模型 (LLM)。

**面向代码的自然语言模型** 专注于学习代码片段的紧凑表示，并直接在代码数据上进行训练。这些模型通过整合诸如抽象语法树 (AST) 和控制流图等结构化信息，从代码片段中提取嵌入。此类模型中的代表是 code2vec [29] 和 code2seq [30]。code2vec [29] 使用神经网络将代码片段表示为固定长度的向量，而像 GGNN（门控图神经网络）[31] 这样基于图的模型则将代码建模为图。这类模型是直接为特定的软件工程任务进行训练和调整的。

**预训练代码模型** 是指在包括 GitHub 和 Stack Overflow 在内的大型软件数据集语料库上，使用自监督学习进行预训练的大语言模型 (LLM)。例如，CodeBERT [32] 是一个在代码和自然语言描述上训练的双峰 Transformer 模型，而 CodeT5 [33] 则将 T5 架构扩展到了代码领域。这些模型使用掩码语言建模或因果语言建模进行预训练。**掩码语言建模 (MLM)** 的做法是在输入序列中遮盖（mask）部分词元（token），并优化模型使其能根据周围（未被遮盖的）词元来预测被遮盖的词元。而**因果语言建模 (CLM)** 则是一种自回归方法，它优化模型使其能在给定前文词元的条件下，预测序列中的下一个词元。在预训练之后，这些模型会在特定任务的数据集上进行微调，以适应专门的下游任务。例如，DeepTyper [34] 就是为类型推断任务进行微调的。

**通用大语言模型 (LLM)** 的训练语料库超越了源代码，涵盖了多种类型，包括科学论文、书籍和更广泛的自然语言文档。这些模型通常包含数十亿个参数，能够执行广泛的自然语言处理任务，而无需针对特定应用进行微调。因此，这些模型能够执行代码之外的下游任务，但也可以通过提示工程进一步专门用于特定任务。

#### 2.2 Metamorphic Testing

蜕变测试（Metamorphic Testing）最初由 Chen 等人 [38] 提出，作为对“谕言机问题”（oracle problem）的一种解决方案，该问题指的是在某些情况下，确定给定输入的输出是否正确是不可行的 [18]。蜕变测试并不直接验证正确性，而是推理输入与输出之间的关系 [19]。例如，为了验证一个计算正弦函数（sine function）的系统，我们可以测试这样一种关系：若 L1 与 L2 满足某个关系 M，则 sin(L1) = sin(L2)。如果系统违反了这种预期的关系，即便没有测试谕言机，这种方法也能识别出错误。

将蜕变测试应用于深度代码模型，涉及到对代码片段进行“保义转换”（semantic-preserving transformations）。这些转换，例如将 `for` 循环替换为等效的 `while` 循环，会保持原始程序的执行行为。然后，通过衡量模型对原始样本和转换后样本的预测是否保持一致来评估其鲁棒性 [9]。

虽然蜕变测试已广泛应用于 Web 服务、模拟与建模、计算机图形学、嵌入式系统和机器学习等其他领域 [19]，但由于代码存在严格的句法和语法约束，它给代码模型带来了独特的挑战。例如，转换必须同时保持代码的语法和语义，这使得这些转换的自动生成和应用变得复杂。此外，转换可能会以特定于任务的方式改变输入-输出行为。Bielik 和 Vechev [39] 展示了用于类型推断任务的转换，例如改变整数字面量，其中改变后的输出对于该任务仍然是有效的。这凸显了蜕变测试对不同上下文的适应性。

目前，蜕变测试主要用于评估鲁棒性，正如本综述所分析的大多数主要研究中所反映的那样。它对保义转换的关注，为深度代码模型的鲁棒性评估提供了一种结构化的方法，解决了软件工程和代码人工智能领域的关键挑战。

图1阐释了应用于深度代码模型的蜕变测试的核心原理。从一个源代码输入开始，“转换选择器/测试用例生成器”首先确定要应用哪些转换。该组件可能使用单次传递、基于采样或梯度信息引导的选择策略。在此指导下，一系列保义转换（例如，变量重命名、无用代码插入或语句重排序）被应用于源代码，以产生逻辑上等价的代码变体。这些变体连同原始代码一起，被传递给被测系统（SUT），这通常是一个深度代码模型，如 CodeBERT 或 CodeT5。然后对输出进行比较：如果模型对语义上等价的输入产生了不一致的预测，则认为测试失败。这种方法无需谕言机标签即可进行鲁ebus评估，而是依赖于转换后输入的语义等价性作为一种隐式的谕言机。

#### 2.3 Scope of !ality A"ributes in Metamorphic Testing

尽管蜕变测试（MT）已被广泛用于评估**鲁棒性** [40, 41]，但其概念框架并不仅限于这一个质量属性。原则上，蜕变测试可以扩展用于评估更广泛的非功能性属性，包括**公平性** [42, 43, 44, 45, 46]、**可解释性**和**幻觉**。

然而，在当前的实践中，尤其是在深度代码模型评估领域，蜕变测试的应用仍主要集中在模型的鲁棒性上。这一趋势也反映在我们的综述中：所分析的全部45篇主要研究都使用蜕变测试来检验模型对输入扰动或保义转换的**韧性**，而非评估公平性或其他属性。

蜕变测试在支持鲁棒性之外的质量评估方面的更广泛潜力仍未得到充分探索，我们鼓励未来的工作研究如何扩展或调整蜕变测试技术，以解决基于大语言模型（LLM）系统中的公平性、幻觉检测和可解释性问题。

#### 2.4 Related Work

研究人员已经从深度代码模型维持其在输入微小扰动下保持性能恒定且正确的能力方面，对其**鲁棒性**进行了研究 [47]。鲁棒性失效可能导致严重问题，例如，对于具有不同编码风格或英语熟练度的用户生成不一致的输出，从而损害其可靠性 [48]。在一些高风险场景中，例如在负责检测受损漏洞的 CI/CD 流水线中，非鲁棒的模型可能会漏掉被修改过的漏洞，导致潜在的危险代码未经检测就通过。

鲁棒性测试通常分为**白盒**和**黑盒**方法 [47, 49]；白盒方法需要完全访问模型的结构、参数和训练数据，而黑盒方法则在无法访问这些信息的情况下工作 [49]。

尽管在评估深度代码模型的鲁棒性和应用蜕变测试方面已有大量的研究工作，但仍然存在显著的空白。Li 等人 [50] 对深度代码模型的鲁棒性进行了一项综述，重点关注用于提升鲁棒性的对抗性训练和修复技术。虽然他们的综述对对抗性方法提供了广泛的概述，但并未审视不同研究中用于测试鲁棒性的转换和方法。同样，Qu 等人 [51] 通过保义转换或对抗性攻击研究了鲁棒性评估，但他们的综述尽管在该主题上投入了大量精力，却未能提供对转换的完整分析或分类。例如，标识符重命名，作为一种流行的转换，在不同研究中的定义和阐述程度不一致，如表5所示。此外，Qu 等人遗漏了本研究中包含的许多相关研究，留下了巨大的覆盖空白。Rabin 等人 [52] 广泛探讨了深度代码模型的属性和质量，包括鲁棒性。然而，其主要焦点是通过实验评估和实现来理解这些模型，而不是进行综述或系统性文献回顾。Yang 等人 [47] 和 Hou 等人 [53] 提供了更广泛的系统性文献综述，关注代码大语言模型的多个方面和不同维度。他们的研究探讨了鲁棒性、安全性、隐私和可解释性。然而，他们的范围超出了鲁棒性，并且不仅仅关注测试方法。

早期的综述如 [23] 通过讨论蜕变测试的主要思想、一般性挑战和未来可能性，对其进行了广泛的概述。然而，我们的研究解决了一个更具体且更及时的课题：**将蜕变测试用于深度代码模型**。与以往的综述不同，我们系统性地审视了**哪些转换被使用、它们是如何被应用的，以及涉及了哪些模型、任务、数据集、语言和评估指标**。这种技术和实证层面的细节是前所未有的。此外，我们对挑战和未来方向的讨论直接基于我们在文献中观察到的模式和空白，而非基于一般性的假设。这使得我们的综述成为关于蜕变测试当前如何应用于深度代码模型评估的**第一篇详细且数据驱动的概述**。

与这些先前的工作相比，我们的研究将焦点专门缩小到蜕变测试，并对其在深度代码模型鲁棒性评估中的应用提供了深入的分析。我们系统地对转换类型进行分类，澄清了不一致的术语（例如，“蜕变测试”与“反事实样本”），并纳入了更广泛、更前沿的研究。这使我们能够填补文献中的关键空白，并提供关于 LLM4Code 蜕变测试实践的**第一篇全面综述**。

### METHODOLOGY


在开展系统文献综述的过程中，我们遵循了由Webster等[54]和Kitchenham等[55]建立的严谨方法论框架。Webster与Kitchenham的研究方法具有互补性：Webster倡导跨学科研究的融合，而Kitchenham则专门针对软件工程领域提出了系统综述的具体技术规范。本研究采用全面无偏的文献分析方法，对深度代码模型的蜕变测试研究进行系统性梳理。

#### 3.1 Research questions

为全面把握该领域的研究现状，我们提出了以下研究问题：
• RQ1：哪些类型的蜕变转换被用于评估深度代码模型的鲁棒性？
• RQ2：在鲁棒性评估中应用转换的技术有哪些？
• RQ3：哪些编程相关任务已通过蜕变测试进行评估？
• RQ4：哪些深度代码模型已通过蜕变测试进行验证？
• RQ5：用于深度代码模型蜕变测试的输入代码涉及哪些编程语言？
• RQ6：哪些数据集被用于生成蜕变转换和评估模型性能？

#### 4.1 RQ1: Types of Metamorphic Transformations

本节基于前述方法论所确定的各项核心研究，针对RQ1系统梳理了使用的蜕变转换技术。我们共从核心文献中识别出121种转换类型（完整清单详见补充材料），并参照Liu等[56]和Quiring等[57]的分类体系进行归类，同时为未能纳入现有分类的转换新增了类别。表5展示了各类别的转换类型数量，具体分类如下：

##### 4.1.1 简单转换(Trivial Transformations)

简单代码转换是通过修改程序底层特征而不影响基本功能的轻量级操作，出现于36%的文献中。典型转换包括：

- 语句调换(Permute Statement)：重排语句顺序保持语义不变（Springer等[58]展示语句重组如何维持程序语义；Rabin等[59,60]通过语法置换和独立语句交换评估模型鲁棒性）
- 展开简写表达式(Unfold Shorthand Expressions)：将紧缩表达式（如a += b）展开为完整形式（a = a + b），研究参见[61-64]
- 操作数交换(Swap Operands)：包括非对称交换（比较运算符操作数调换，如a > b → b < a，见[56,65,64]）和对称交换（交换交换律运算符操作数，如a + b → b + a，见[61,66]）
- 移除未使用代码(Remove Unused Code)：删除未使用的变量/函数/库（[56,57,67]）
- 声明拆分/聚合(Split/Aggregate Declarations)：调整变量声明方式（如int a, b → int a; int b，见[56,62]）
- 声明与初始化分离(Split/Aggregate Declaration and Initialization)：修改初始化模式（如int a = 1 → int a; a = 1，见[62,64]）
- 前后缀交换(Exchange Suffix/Prefix)：替换自增/自减运算符（如i++ → ++i，见[65,62]）
- 添加中性元(Add Neutral Element)：在逻辑表达式中添加中性元素（如true → 0^1 == 1，见[8,9]）

##### 4.1.2 标识符重命名(Identifier Renaming)

该类别转换覆盖86.5%的研究文献。我们突破既往研究[51]的单一分类模式，依据重命名策略对模型行为的显著影响进行细分：

- 基于策略的重命名：采用特殊技术替换标识符[65,77-85]
- 近义词替换：改用语义相近词汇[77,86,87]
- 模板值替换：如int a → int var1[88,57,89]
- 随机标识符替换：从数据集中随机选择新标识符[90,91,57]
- 混淆处理：用随机字符序列替换（如int test_counter; → int Bq41wD7l;[56,69]）
- 变量重命名：直接更改变量名[76,58,75,74]
- 局部变量/参数/字段重命名[73]
- 语义保持标识符重命名：在嵌入空间施加对抗扰动[71]
- API/参数/方法名重命名：分析模型对语义迁移的处理能力[72]
- 系统化/任意重命名：测试语义等价性[59,60,70]
- 词汇表重命名：使用预定义词汇替换[92,8,9]
- 上下文命名：如int count → int count_var_1[88]

##### 4.1.3 注释转换(Comment Transformations)

约9%的研究涉及注释转换，包括内容/位置/结构修改：

- 删除注释(delete comment)：完全移除注释[8,64]
- 添加注释(add comment)：增加新注释测试模型注解处理能力[8]
- 移动注释(move comment)：改变注释位置以调整上下文关联[8]
- 注释内词序调整(move word in comment)[91]
- 注释内词汇删除(delete word in comment)[91]
- 注释内词汇复制(copy word in comment)：制造冗余测试模型反应[91]
- 注释插入/删除/置换组合操作[93]

##### 4.1.4 数据转换(Data Transformations)

45.5%的研究采用此类转换，通过改变数据表示方式测试模型适应性：

- 显式类型转换(use cast expressions)：如b = (int) a[56,68]
- 字符串转字符数组(Convert string literals to char arrays)[56,57]
- 字符转ASCII值(convert char literals into ASCII values)：如char c='A' → char c=65
- 整数字面量转表达式(convert int literals into expressions)：如int b = 8 → int b = 2 * 4
- 整数转十六进制(convert integers to hexadecimal numbers)：如int b = 48 → int b = 0x30
- 动态类型表达式(use typed expression)：如typeid(a) b = 0[56]
- Def-Use链断裂(Def-Use Break)：测试变量关系变更的恢复能力[70]
- 布尔值交换(boolean Exchange)：如true ↔ false[60,59,58,76]
- 类型转换(type conversions)：如bool转int[93]
- 字符串编码(EncodeStrings)：用函数调用替换字面字符串[94]
- 冗余表达式(plus zero/return optimal adding)：如a = a + 0[72]
- 数据流操作(data flow operations)：应用于代码归属分析、克隆检测等任务[74]
- 关系运算符切换(relational operator switching)：如a < b → b > a[75]
- 等值赋值插入(inserting equal assignments)：如b = -10; → b = b - 10[75]

##### 4.1.5 控制流转换(Control Flow Transformations)

58%的研究使用此类转换，通过改变执行流程测试程序逻辑处理能力：

- for/while循环互转(convert for-statement to while-statement)[56,65,61,66,57,89,62-64]
- if-else/switch-case互转(convert if-else to switch-case)[56,61,89,62,64]
- 循环类型替换(loop exchange)[76,58,75,59]
- 独立语句调换(swap independent statements)[61,91,89,64]
- if条件拆分(split conditions of if-statements)：如if(a && b) → if(a) if(b)[56,57,62]
- if-else转三元表达式(convert if-else to conditional expression)：如condition ? a : b[56,62]
- 条件包装(wrap expression in if statement)：如if(true)包裹代码[8,9]
- lambda包装(wrap expression in lambda)[8,9]
- if-else体交换(swap if-else bodies)：同时取反条件[56]
- 结构重组(flatten/MergeSimple)：重组语句与函数[94]
- 分支结构修改(If-Else Flip)[70]
- 混淆条件(obfuscated conditions)：改变程序逻辑但不影响静态分析复杂度[95]

##### 4.1.6 函数转换(Function Transformations)

24.5%的研究涉及函数级转换，测试模型对函数结构/语义变化的适应性：

- 增加函数参数(Add Function Arguments)：从词典或程序推断添加参数[8,9]
- 代码块委托(Delegate to Function)：将代码块提取为独立函数[8,9]
- 参数合并(Merge Function Arguments)：合并参数为结构体[56]
- 参数重排序(Reorder Function Arguments)[56]
- 二元表达式转函数(Convert Binary Expressions into Functions)：如c = add(a, b)[56]
- 函数调用图修改(modify Function Call Graph)：添加预设函数[95]
- 参数操作(RndArgs/MergeSimple等)：操纵函数参数与结构[94]
- 代码片段提取(extract snippets into new functions)[93]
- 独立语句块交换(Independent Swap)[70]

##### 4.1.7 API转换(API Transformations)

仅6%研究使用，是最罕见的转换类型，主要针对C/C++接口等效替换：

- C/C++库函数交换(Swap C/C++ Libraries for Reading and Writing)：如printf ↔ cin/cout[57,62]
- 控制台I/O替换文件I/O(Use stdin/stdout Instead of Files)[57]
- 流同步启用/禁用(Enable/Disable Sync Between C/C++ Streams)[57]

##### 4.1.8 死代码插入转换(Dead Code Insertion Transformations)

64.5%研究使用的重要类别，通过插入永不执行的代码测试冗余处理能力：

- try-catch陷阱("try-catch trap")：插入未执行函数调用[95]
- 未使用语句(Unused Statement)：添加不可达块[76]
- 假条件块(if (false) blocks)[75]
- 冗余模式构建(redundant constructs)：如if(false){...}[74]
- 垃圾代码(junk code)：包括无用变量或打印语句[73]
- 不可达代码(unreachable code)：如if (1==0): print(0)[72]
- try-catch块插入[60]
- 添加死代码块(Add Dead Code)：如if(false){...}[78,66,79-81]
- 添加打印语句(Add Print Statement)[78,88,79-81]
- 添加未使用变量(Add Unused Variable)：按策略[66,81,82]、词典[8,9]或程序上下文命名[8,9]
- 冗余库导入(Add Libraries)[56,57]
- 外部代码移植(Transfer Code)：将无关代码插入不可达区域[96,61]
- 不可达循环/分支插入(Insert Unreachable Loop or Branch)[97,81]
- 空语句/分支/循环操作(Insert or Delete Empty Statement/Branch/Loop)[97,92]

##### 4.1.9 杂项转换(Miscellaneous Transformations)

20%研究包含的非常规转换，虽简单但影响模型性能：

- 空白符增删(Add or Remove Whitespace)[8]
- 复合语句增删(Add or Delete Compound Statement)：调整大括号范围[57]
- 格式修改(altering formatting)[93]
- 主函数显式返回(Add Explicit Return to Main Method)[57]
- 返回字面量转变量(Replace Literal Return with Variable)[57]
- 语句重排(Statement Permute)[76,75]
- 嵌入空间梯度扰动(gradient-based virtual perturbations)[71]
- 表达式分割/声明合并(dividing expressions/merging variable declarations)[75]
- 自动格式化(Auto-Format Code)[67]
- 删除打印语句(Delete Print Statement)[64]

研究发现标识符重命名和死代码插入是最常用转换类型，因其能最大程度欺骗模型且支持跨标签代码特征迁移。



RQ1结论：蜕变转换类型呈现高度多样性。死代码插入(64.5%)、标识符重命名(86.5%)和控制流转换(58%)应用频率最高；简单转换(36%)、数据转换(50%)和函数转换(24.5%)广泛用于基线与语义测试；API与注释转换(各6%)发展最不充分；杂项转换(20%)涵盖异质化研究特定操作。



研究建议：未来工作应重点发展API转换、注释转换等薄弱类别，超越常用技术构建更全面的鲁棒性评估框架。具体方向包括：
• 拓展转换谱系：开发API重写、注释/空白编辑、整体函数重构等模仿现实重构的操作
• 深化语义测试：突破表层修改，关注数据流、控制流和资源相关的行为保持转换（如循环展开、记忆化）
• 量化转换质量：结合自然度、编译率、可读性指标补充成功率评估
• 跨语言工具开发：突破当前Java/Python中心格局，支持JavaScript/C#/Go等语言的AST级转换
• 组合转换研究：探索多转换叠加的协同效应，自适应调度算法可能揭示单步测试未发现的复合漏洞
• 共享实验构件：公开转换语料库、参考实现和有效性检查工具，促进对比研究与累积进展



#### 4.2 RQ2: Application Techniques for Metamorphic Transformations

本节重点分析用于实施蜕变转换以评估深度代码模型鲁棒性的技术方法（即应用技术），涵盖转换的选择、排序与执行策略。这些技术在复杂度上呈现梯度分布：从简单无反馈的单次应用方法（统一或随机施加转换），到进化算法驱动的优化组合策略，再到针对模型敏感特征的梯度引导技术。部分研究采用随机死代码插入等无反馈操作，而另一些则利用梯度信息或模型置信度指导定向标识符重命名。为提升清晰度，我们将其分类阐述并附示例。需注意[88]、[68]及[39]等研究未明确描述转换应用方法。

**4.2.1 单次应用技术(One-pass Techniques)**  
该技术以设计简单、无优化或反馈循环为特征，随机或系统化应用预设转换集而无迭代改进。例如：  

- Applis等[8]使用固定转换集评估程序分析任务的模型鲁棒性，强调统一转换  
- Gao等[90]采用随机替换策略，从数据集中无指导地系统替换标识符  
- Jin等[67]应用最多20种固定转换（含变量重命名和死代码插入）生成对比预训练增强数据集  
- Liu等[91]随机应用固定转换集生成语义等价代码变体  
- Rabin等[89]在程序单位置或所有合规位置系统化应用转换，仅依赖预定义规则  
- Li等[95]实施死代码插入和无价值调用等简单转换，保持无指导特性  
- Pei等[76]使用变量重命名和语句置换等无反馈技术  
- Springer等[58]采用循环交换和变量重名的固定策略  
- Le-Cong等[75]系统应用预定义转换（变量重命名、添加未使用语句、if(false)语句交换）  
- Nguyen等[74]聚焦简单变量重命名策略  
- Zhang等[73]通过随机死代码插入和直接重命名任务体现无指导特性  
- Li等[94,93]基于预定义转换开发系统化应用技术  
- Rabin等[59,60]展示布尔值交换和循环交换等简单转换的系统化应用  
- Hooda等[70]采用语义保持突变（如if-else翻转、随机变量名）的固定策略  

这些基于采样的技术侧重简洁性、一致性和易用性，虽适用于基础鲁棒性评估，但缺乏基于优化或迭代反馈的高级方法的适应性与有效性。

**4.2.2 进化技术(Evolutionary Techniques)**  
利用进化算法通过优化适应度函数决定转换策略：  
- Applis等[9]使用遗传算法寻找成功转换集，适应度函数最大化F1分数下降，个体表示为AST转换序列  
- Ferretti和Saletta[96]采用语法进化（遗传算法）注入代码片段，以模型置信度为适应度函数  
- Li等[95]提出Apoem框架利用多群体协同进化算法构建对抗变更，考虑多粒度实现鲁棒对抗样本生成  
- Yang等[85]采用混合策略：先通过贪婪搜索识别关键标识符（替换为无信息词符测量置信度变化），若无预测变化则用遗传算法优化变量替换组合（个体编码为原变量-替换对集合，以模型置信度为适应度函数）  
- [84]使用掩码方法检测重要标识符（替换为<UNK>词符评估因果效应），基于此生成扰动标识符初始种群并应用NSGA-II算法[98]优化对抗损失、语义相似度和修改率  

这些方法展现了进化算法在明确目标驱动下构建有效转换流程的能力。

**4.2.3 梯度引导技术(Gradient-Based Techniques)**  
依赖输入梯度计算决定转换策略：  
- Yefet等[82]利用梯度计算标识符损失，通过嵌入空间局部搜索寻找最大破坏性词符  
- Chen等[65]计算雅可比矩阵定位关键词符，应用Yefet方法替换标识符，针对性实施结构转换最大化影响  
- Henkel等[78]随机采样转换序列（如10组5转换序列），采用梯度方法解决转换产生的不一致性  
- Liu等[56]训练代理模型近似受害者分类器，利用雅可比矩阵识别重要特征（如标识符），迭代选择最大化累积特征重要性的转换直至预测改变  
- Li等[71]直接使用基于梯度的对抗训练范式，采用投影梯度下降(PGD)计算嵌入空间扰动，系统生成对抗样本  
- Yang等[72]通过对抗训练等梯度方法识别重要特征并系统操控，提升模型鲁棒性  
- Nguyen等[74]在CARROT框架中纳入梯度引导转换（如梯度引导标识符重命名和死代码插入），但黑盒设置下未直接使用，凸显了梯度技术在无模型访问场景的局限性  

**4.2.4 采样引导技术(Sampling-Based Techniques)**  
通过特定分布采样决定标识符替换：  
- Zhang等[83]引入Metropolis-Hastings蒙特卡洛(MHM)方法，从词汇表随机选择新标识符，以模型置信度下降概率接受替换  
- Ding等[77]基于MHM创建代码变体，但约束替换为语义相似词  
- Zhang等[92]扩展MHM方法，在嵌入空间利用梯度信息引导新标识符选择，同时随机应用结构转换增加多样性  
- Nguyen等[74]采用基于采样的策略，根据统计分数的影响力估计选择攻击位置和模式  
- Le-Cong等[75]对部分转换（如变量重命名）采用采样策略，从预训练模型（如CodeBERT的RenameVariable-2）的分布中随机采样替换  

这些方法结合概率采样与语义相似性/梯度信息等约束，系统检验标识符替换效果。

**4.2.5 迁移引导技术(Transfer-Based Techniques)**  
通过跨代码片段特征迁移误导模型：  
- Gao等[61]采用降低预测概率标准差的转换识别代码片段显著特征，将其他程序的显著特征作为死代码插入以误导模型  
- Na等[97]通过添加无信息词符识别易感位置，向关键位置添加无关程序的显著特征  
- Tian等[63]从模型预测的次大概率类寻找参考输入，通过转换使被攻击输入镜像参考输入  

这些方法通过特征迁移干扰模型感知，有效评估对抗攻击韧性。

**4.2.6 嵌入引导技术(Embedding-Based Techniques)**  
最大化原始与重写代码在嵌入空间的距离：  
- Jia等[80]融合Henkel等[78]和Srikant等[79]技术最大化输入程序在嵌入空间的差异  
- Springer等[58]使用词符嵌入（如L2范数）进行对抗词符替换  
- Pei等[76]采用Aut(PDG)-等变自注意力层确保语义有效性，研究嵌入空间表示分析鲁棒性  
- Le-Cong等[75]使用语义保持转换（如基于CodeBERT的变量替换）  
- Li等[71]处理嵌入空间方法，针对编程语言模型嵌入进行语义保持的系统扰动测试  
- Yang等[81]使用遗传算法寻找嵌入空间差异最大的名称，并通过代理编码器验证；在关键位置嵌入代码片段（通过解释性词符注入识别），检查插入导致的损失增加  

这些方法通过嵌入空间操控有效测试模型在结构保持语义转换中的弱点。

**4.2.7 混合技术(Miscellaneous Techniques)**  
涵盖上述未包含的多样技术：  
- Quiring等[57]使用蒙特卡洛树搜索[99]迭代选择最可能改变预测的转换  
- Srikant等[79]采用交替优化寻找最具影响的位置和转换  
- Zhang等[86]通过替换无信息词符识别脆弱标识符，用CodeBERT微调生成上下文相关替换  
- Zhang等[64]对比随机搜索、编辑距离最大化的遗传算法、困惑度最大化的MCMC算法、以及差异和克隆检测奖励的深度强化学习算法（均未使用模型反馈）  
- Zhou等[87]基于标识符与程序嵌入的余弦距离检测替换重要标识符  
- Liu和Zhang[66]设计结构突变生成多样代码片段，通过训练网络寻找易误分类样本并强化填充  
- Tian等[62]将对抗样本生成建模为马尔可夫决策过程，使用Q学习并以模型置信度下降为奖励  
- Wei等[69]聚焦激活最多新神经元的转换以彻底探索代码空间  

**RQ2结论**：蜕变测试技术在复杂度和应用方式上差异显著。最常用的是无优化反馈的单次应用技术，更复杂的方法采用进化算法等优化技术迭代改进转换，以及梯度引导技术。采样引导、嵌入引导、迁移引导及混合技术应用频率较低。

**研究建议**：未来工作应系统比较这些技术并在效率、效果和泛化性间权衡。具体方向包括：  
• 建立系统基准：创建公共基准（模型/任务/数据集），报告查询预算、运行时间和成功标准，使各类技术可公平对比  
• 开发混合流程：组合互补思想（如用梯度显著性播种进化搜索，将嵌入距离目标纳入遗传适应度）  
• 适应黑盒约束：针对仅暴露logits或最终预测的工业LLM，探索高效代理模型和迁移策略  
• 利用静动态分析：通过传统程序分析线索（def-use链、控制依赖、污点流）指导转换选择并缩减搜索空间  
• 追踪效率指标：报告成功测试的查询数、变异词符数和耗时，现实管道需平衡效能与成本  
• 开源工具：发布生成器、适应度函数和评估工具链加速复现并驱动事实标准  
• 研究泛化能力：测试MT技术跨语言/模型/任务的迁移性

#### 4.3 RQ3: Investigated Programming-related Tasks

表6展示了被测模型执行的下游任务，补充材料包含这些任务的模型鲁棒性评估指标及模型输入对比指标。我们发现最常测试的任务是克隆检测、方法名预测和代码归属判定，分别占文献总量的29%、29%和18%。这种分布可能源于广泛认可的基准数据集的可获得性，例如克隆检测的BigCloneBench[100]、方法名预测的code2vec[29]训练数据集，以及代码归属判定的Online Judge数据集[101]。  

具体而言：  
- **克隆检测**涉及识别重复或相似代码片段，对维护代码质量和消除冗余至关重要[74]  
- **方法名预测**根据函数内容预测描述性名称，提升代码可读性和可维护性[60]  
- **代码归属判定**确定代码片段作者，应用于抄袭检测和软件取证[74]  

其他重要任务中：  
- **代码摘要**（18%）生成代码函数的自然语言描述，是文档化和理解复杂代码的关键环节[93]  
- **功能分类**（11%）基于功能对代码片段分类，助力大规模代码库的理解和组织[66]  
- **缺陷检测**（13.5%）专注于识别代码错误以提升软件可靠性[71]  
- **漏洞检测**（13.5%）揭示代码安全漏洞，维护软件完整性并降低攻击风险[94]  

关注度较低但仍被研究覆盖的任务包括：  
- **代码补全**（9%）预测后续代码词符或语句，辅助开发过程[70]  
- **代码翻译**（6.5%）实现编程语言间转换，增强软件互操作性[72]  
- **代码修复**（4.5%）自动修正代码错误，常利用模型生成改进方案[75]  
- **注释生成**（2%）为代码片段创建解释性注释，改善文档质量[87]  
- **类型推断**（2%）预测变量/函数的类型注解，辅助代码维护与重构[39]  
- **代码搜索**（6.5%）在大型仓库中查找相关代码，促进代码复用和开发效率[93]  

若干小众任务（各占2-3%）同样被研究：  
- **恶意软件检测**识别程序中的恶意代码，增强软件安全性[95]  
- **函数相似性检测**识别语义等价函数以优化重构[76]  
- **函数签名预测**预测函数的输入输出类型，提升API可用性[76]  
- **内存区域预测**预判程序访问的特定内存区域，用于底层系统优化[76]  
- **代码问答**回应关于代码片段的疑问，辅助调试和复杂逻辑解释[71]  

**RQ3结论**：蜕变鲁棒性评估中最常测试的任务是克隆检测（29%）、方法名预测（29%）和代码归属判定（18%），这些任务的流行可能源于成熟基准数据集的存在。  

**研究建议**：当前研究集中于少数主导任务，表明深度代码模型的蜕变测试缺乏任务多样性。将评估范围扩展至低覆盖任务（如代码修复、恶意软件检测、内存预测）或全新任务（代码生成、测试用例生成），可揭示新的鲁棒性漏洞并改进泛化能力评估。具体方向包括：  

- **拓展任务覆盖**：将MT研究延伸至高价值低覆盖任务（代码生成、程序修复、测试用例合成、性能优化、恶意软件/漏洞缓解），这些场景考验不同推理能力并可能暴露新鲁棒性缺陷  
- **安全关键评估**：在具有实际安全影响的任务（缺陷/漏洞/恶意软件检测）上评估蜕变转换下的鲁棒性，其中假阴性会带来现实风险  
- **端到端管道**：超越单步任务，评估开发工作流（如补全→编译→单元测试）中的MT效应以捕捉错误传播  
- **多任务多语言套件**：发布共享基准集合，为每个任务配备语言多样、支持转换的数据集，实现系统化的跨任务鲁棒性对比  
- **任务特定蜕变关系**：针对新兴任务语义设计转换族，例如代码翻译的API级重写或规范驱动合成的逻辑后置条件置换
